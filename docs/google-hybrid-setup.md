# Sarathi: local storage, Google Drive and Calendar

1. Keep `APP_URL=http://localhost:8080` for local use. In Google Cloud's Web OAuth client, register `http://localhost:8080/api/google/callback` as an authorized redirect URI. Configure `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in the server's `.env.local`.
2. Enable Google Drive API and Google Calendar API. While the Google app is in Testing, add every account that will authorize Sarathi as a test user.
3. Run the existing documents migration and session-token migration in Supabase if needed: `202610040002_healthnest_documents.sql` and `202610040003_drive_session_tokens.sql`. Only account identity and the repository folder ID are stored in `drive_connections`; refresh tokens and Drive file content are not stored.
4. Log in to Sarathi, open Documents, review the Google connection consent, select Calendar sync if wanted, then click Connect Google. The account owner completes Google's permission screen. Google access expires with the original ten-minute Sarathi session, even if authorization is completed partway through it.
5. Select Local documents or Google Drive documents before uploading. Local mode works without Google. Drive mode creates `<Patient>/<Year>/<Document Type>` folders beneath the Sarathi repository and uploads directly to Drive without saving a local file or document metadata entry. Refresh scans Drive folders anew. Choose an optional private base-folder link in Profile before the first connection; otherwise a Sarathi folder is created in My Drive.
6. Medical Report and Prescription uploads create the existing prototype care-task templates. Authorized Calendar sync copies these new tasks to the connected account's primary Calendar. Voice simulation bookings also create a care task after confirmed simulated availability, then sync if authorized. These remain simulated provider bookings.
7. Existing tasks have a Sync to Google Calendar button. Retries use a deterministic Google event ID so the same task is not duplicated. A failed sync preserves the local task and displays a retry message. No Google event is removed by the two-hour temporary follow-up cleanup.
8. Drive summaries and visit-brief reading happen in the authorized session. Drive documents are read in memory; supported formats use the existing local extraction and redaction before Groq. Manually uploaded files are counted, but Google-native document types must first be exported as PDF for reading.

Local member sharing remains separate from Google Drive sharing. Existing verified Setu consent and recipient acceptance protect local repository access; inviting a local member does not grant Drive permission. Invitation/revocation emails use `SMTP_USER` and its Gmail app password in `SMTP_PASS`. Email failures do not undo sharing decisions and can be retried in Members. Email addresses alone never authorize Drive or Calendar.

Validation: `npm run test:repository`, `npm run test:google`, `npm run test:rails`, `npm run typecheck`, and `npm run build`. Google checks use mock responses and do not create real files or Calendar events. Live OAuth completion, upload and event creation require the account owner's authorization in the browser.
